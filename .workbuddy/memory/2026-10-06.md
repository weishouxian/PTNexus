## 「未找到可用于分析的媒体文件」根因：下载器容器内路径 vs 代理可见路径

**结论**：报错来自 `processing/media/iso_session.go:resolveMediaTargetByCandidateList`（三条候选 torrent_name/content_name/save_path 全部 stat ENOENT）。根因是下载器给的路径（容器内 `/downloads/complete/...`）在「代理侧」和「PTNexus 本地侧」都无法落地，不是 PTNexus 代码 bug。

**2026-10-06 在 5.135.178.15 实测（关键事实，勿再重复探测）**
- Transmission 容器（lscr.io/linuxserver/transmission:4.0.5）：宿主 `/srv/transmission/downloads` → 容器 `/downloads`；`settings.json` `download-dir=/downloads/complete`；`.resume` 里 `destination=19:/downloads/complete` → **API 报出的是容器内路径**。
- 宿主机 `/downloads` 是**软链 → `/home/app/download/`（qbittorrent 的下载池）**，`/home/app/download/complete` 不存在 ⇒ 代理在宿主机上把 `/downloads/complete/...` 解析到 qb 池 → 必失败。
- 盒子代理 `pt-nexus-box-proxy` 以**裸进程**跑在该机（cwd `/opt/pt-nexus-proxy`，宿主 mount ns，PPID=1）。实测 `POST /api/media/mediainfo`：`/downloads/complete/银翼杀手2…` → `stat … no such file or directory`；`/srv/transmission/downloads/complete/银翼杀手2…` → **success 并成功提取 MediaInfo（DV Profile 5 也 OK）**。
- 该机**没有 pt-nexus 容器、5274 无监听**（PTNexus 不跑在这台）。Windows 下 `os.Stat` 报的是 `GetFileAttributesEx … The system cannot find the path specified.` ⇒ 用户看到 `stat …: no such file or directory` 说明 PTNexus 进程在 **Linux**。

**机制**：`refresh_flow.go` 先拿**未翻译**的 save_path 当 `remote_path` 打代理（刻意，见该处注释），代理失败才用 `path_mappings` 翻译后的路径做本地扫描；用户配的映射（`/downloads` → `/srv/transmission/downloads`）只服务本地扫描，所以两条路都断。`use_proxy=false` + 无映射时本地扫描同样报这条消息。

**候选修法**：① 宿主机 `ln -s /srv/transmission/downloads/complete /home/app/download/complete`（零停机，让代理能解析容器路径，老/新种子都通，建议连 `incomplete` 一起）；② TR 容器加同路径挂载 `/srv/transmission/downloads:/srv/transmission/downloads` + 改 download-dir（老种子仍用旧挂载）；③ 代码侧让代理候选同时带上「路径映射后的路径」（`buildRemotePathCandidates` 调用处 + 截图链路同步改）。

## 方案 ③ 上线后仍报同错：真因是「代理把候选路径不可达报成 HTTP 500」

**现象**：同一 seed 重试仍返回 `未找到可用于分析的媒体文件 … GetFileAttributesEx …`（GetFileAttributesEx = 报错进程在 Windows，即用户本机跑的调试实例）。

**日志铁证**（`server/data/logs/ptnexus.log` 7654-7678）
- `路径映射完成 original_save_path=/downloads/complete translated_save_path=/srv/transmission/downloads/complete` ✅ 候选生成没问题。
- `盒子代理提取失败 remote_path=/downloads/complete/银翼杀手2… status=500` → 只试了**第一个**候选就断了，映射后那条能成功的候选**根本没被请求**。

## 桌面端报 `server health check failed: timeout waiting for 127.0.0.1:5275` 的根因

**症状**：双击 `desktop/build/bin/pt-nexus.exe` 后 GUI 起来了，但后端连不上；日志
`%APPDATA%/PT-Nexus/data/logs/ptnexus.log` 每 **12 秒**重复一次（12s = 旧 `waitHTTPReady` 超时，说明壳在不停 kill+重启 sidecar）。

**根因**：`server/cmd/server/main.go:loadEnvFiles()` 会从 cwd 向上 10 层找「go.mod + internal + cmd/server/main.go」的 server 根目录；exe 放在 `desktop/build/bin` 时**向上命中了仓库的 `D:\MYCODE\PTNexus\server`**，于是加载了 `server/.env`（`DB_TYPE=mysql` + 内网 MySQL）。
而 `repository/db.go:NewStore()` 的判定顺序是 **`DB_TYPE` 环境变量 > desktop 的 `database.json` > sqlite**，所以桌面端的 `database.json`（sqlite）被完全绕过 → 连内网 MySQL 阻塞 >12s → 5275 起不来。

**修复（已实施，全部在 `desktop/` + 构建脚本）**

| 文件 | 改动 |
|---|---|
| `desktop/internal/desktopapp/embedded_server.go`（新） | `StartEmbeddedServer`：import `github.com/pt-nexus/server/internal/bootstrap` 进程内起 Gin 监听 127.0.0.1:5275；`isolateDatabaseEnv` 在 database.json 有 type 时清掉 `DB_TYPE`/`MYSQL_*`/`POSTGRES_*` |
| `desktop/internal/desktopapp/bundle.go`（新） | `//go:embed all:bundle` + `MaterializeBundledResources`：把内嵌站点资源配置展开到 `%APPDATA%/pt-nexus/resources`（每次启动覆盖） |
| `desktop/internal/desktopapp/bundle/`（新，632K） | 从 `server/sites_data.json` + `server/configs/`（73 个 yaml）同步而来，**提交进仓库**（go:embed 需要文件存在） |
| `desktop/internal/desktopapp/runtime_env.go` | `resolveDesktopResourceDir` 优先级改为：`PTNEXUS_RESOURCE_DIR` > 内嵌资源展开目录 > `../server` > exeDir |
| `desktop/internal/desktopapp/sidecars.go` | `StartServerSidecar` 优先内嵌，失败回退外部 `server.exe`（原逻辑抽到 `startExternalServerSidecar`，超时 12s→30s） |
| `desktop/app.go` | `startup` 只把 server 当必需；updater 缺失降级提示，不阻塞主流程 |
| `scripts/package-desktop.sh` | 新增 `single` 子命令（只出单文件 exe，不需要 wails/NSIS/rsync）；新增 `sync_embedded_bundle` 并在 `prepare_sidecars_stage` 调用；`rsync` 全部改为 `sync_tree`/`sync_frontend_dist_tree`（缺失自动退回 `cp`） |
| `desktop/README.md`、`desktop/docs/build.md` | 重写，记录两种分发形态与环境变量隔离约定 |
