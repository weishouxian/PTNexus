## MediaInfo / BDInfo 判媒介的边界

- **MediaInfo**：能可靠给流层属性（视频/音频编码、分辨率、HDR 格式、音轨数语言）；媒介层只能概率推（Encode 看 Video 段 `Writing library`/`Encoding settings`；Remux 看「无编码器信息 + 无损原轨 + 高码率」）；**判不出来源**（BluRay 与高码 WEB 的流同构）、判不出原盘结构（蓝光 ISO 直读只出 General）。
  - ⚠️ 修正：`General → Writing application: mkvmerge/MakeMKV` **不是** Remux 专属指纹 —— 压制组同样用它封装 x264 输出。真正的分水岭是 Video 段 `Writing library` / `Encoding settings` 的有无。
- **BDInfo**：描述的是**碟**，不是种子封装形态。它能硬判「源盘 = 原盘」，但**判不出种子里装的是 ISO/BDMV 还是 Remux 后的 mkv**。
  - ⚠️ 关键坑：源站详情页常挂**源盘 BDInfo**（种子本体是 Remux，详情里贴的却是源盘碟信息）。拿 BDInfo 判 `medium` 会把这类 Remux 种子整批误判成原盘 → medium 主源必须是标题/站点字段，BDInfo 只能做正向确认（且需先确认种子文件为 ISO/BDMV）。
- 判读经验（本次样张：`iso-4207589629`，27,297,207,696 B / 97min / 单 MPLS 00000 / AVC 29.4Mbps / TrueHD-Atmos 7.1 单音轨 / 1英4中字幕）：
  - 碟大小 27.3 GB **超过 BD25 上限（25 GB）**又远不满 BD50 → 非商业碟顶格容量特征；
  - 碟大小 − 唯一 playlist 大小 = 85,392 B → 全碟只有这一条正片流，无菜单/BD-J/花絮/多 playlist；
  - Disc Label 是 `iso-<数字>` 而非规范片名；单音轨 + 多中字 → 指向 **DIY/精简原盘**，非商业原盘全碟。
- ⚠️ **`medium.bluray_diy` 是「只进不出」的标准值**：站点适配器（ttg/baozi/hdhome/hdfans）都在消费它，但 `inferStandardizedValues` 的 medium switch（`review_extract.go:2631-2654`）**没有任何分支能产出它** —— 只能靠站点字段映射（如 1ptba `"BD DIY"→medium.bluray_diy`→19、audiences→14、baozi→13）进入。所以标题侧推断永远出不了 DIY 档。
- 若要支持「标题标 Remux、实体是 ISO 原盘」的纠偏：`acquire/fetch/torrent_video_size.go` 已有解析 torrent 文件列表的能力（`videoFileExts` 含 `.iso`），可在同层加「碟结构探测」（单文件 `.iso` / `BDMV/` + `CERTIFICATE/` 目录）作为**正向覆盖**信号；注意仅在前者确认时为原盘，不能反向用 BDInfo 覆盖。

## 站点保存报「未找到站点ID '43' 或更新失败」

- 现象：站点设置保存失败，报 `未找到站点ID '43' 或更新失败。`（id=43 = 人人）。
- **根因不是 SQL 错误，也不是 dupe 引入的**：`UpdateSiteDetails` 末尾 `return result.RowsAffected > 0, nil`。`repository/db.go` 的 MySQL DSN **未开 `clientFoundRows`** → 提交值与库内完全相同时 MySQL 只计「真正改变的行」，返回 **0**，于是被判定成「站点不存在」。
- 实测证据（内网 MySQL `192.168.5.3`）：
  - `dupe_check_enabled` / `dupe_size_tolerance_bytes` 两列**已存在**（schema_manager 的 ALTER 补列已生效），`id=43` 记录存在。
  - 用代码实际发出的完整 UPDATE 语句（参数取库内现值）执行 → **无 SQL 错误，但 `rowcount=0`**；把某字段改成不同值 → `rowcount=1`。
  - 即「打开弹窗不改任何配置直接保存」必现该报错；改任意一个值即可成功。
- 修复（`server/internal/repository/site_repository.go`）：
  - `UpdateSiteDetails` 改为 UPDATE 成功后**按主键回查** `siteExists(siteID)` 返回存在性，而不是看 RowsAffected。
  - ⚠️ 第一版直接 `return true, nil` 是错的 —— 临时测试立刻暴露「不存在的 id 也返回成功」，会把真正的「站点不存在」一起吞掉；改成回查后两类场景都正确。
  - 同源问题一并修：`UpdateSiteCookie`（按 nickname 回查）、`UpdateSiteCookieBySite`（按 site 回查）—— 否则重复同步同一份 Cookie 会被误报「未找到站点」。
  - `DeleteSite` 保留 `RowsAffected > 0`：DELETE 删 0 行确实意味着记录不存在，语义正确。
  - `server/internal/http/handler/sites_handler.go:UpdateSite` 把 `err != nil` 与 `!updated` 拆开：DB/参数错误回 500 并**如实带出错误信息**，不再与「未找到站点」混成同一条 404 文案（原先真实原因会被这文案掩盖，这是本次排查绕路的原因）。
