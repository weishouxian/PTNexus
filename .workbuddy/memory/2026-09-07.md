## 踩坑记录（本机网络环境）

- 本地代理 `http://127.0.0.1:8496`（WorkBuddy 注入）只放通 `api.github.com` / `objects.githubusercontent.com` / `uploads.github.com`，**`github.com` 主站 CONNECT 返回 502**。代理进程会时断时续，断的时候直连可通但 `github.com` 仍不稳。
- curl 必须加 `--ssl-no-revoke`，否则 schannel 报 `CRYPT_E_REVOCATION_OFFLINE`。
- Git Bash 下 `curl -o /dev/null` 会报 `(23) client returned ERROR on write`，导致 `HTTP=000` 误判；要写到真实文件再看结果。
- 下载 Release 大附件（几 MB 以上）必须加 `--http1.1`，HTTP/2 会卡死在 288 KB。
- `%USERPROFILE%\.config\gh\hosts.yml` 写不进去（沙箱拦截），gh 登录必须指定 `GH_CONFIG_DIR` 到可写目录。
- 新建**全新 tag** 的 Release 可能需要 `workflow` scope（`--web` 登录默认只有 `gist, read:org, repo`），用 `gh auth refresh -h github.com -s workflow` 补。

## 修复：安装脚本 CRLF 导致 Linux 上 `curl | bash` 失败（23:05）

- 现象：Linux 执行报 `bash: line 2: $'\r': command not found`、`syntax error near unexpected token`。
- 根因：仓库开了 `core.autocrlf=true`，工作区 `.sh` 被检出为 CRLF；**git 索引里的 blob 一直是 LF（正确）**，但我上传 Release 附件时用的是工作区 CRLF 文件，导致线上是 CRLF。
- 修复：工作区文件转 LF 后重传，线上 16,069 → **15,484 B**（去掉 585 个 CR），已验证纯 LF。
- 防复发两层：
  1. `.gitattributes` 加 `*.sh text eol=lf`（原来只有二进制的 merge=ours 规则）。
  2. `github-release` 技能的 `publish.sh` 增加检测：`.sh` 附件含 CR 时自动 `tr -d '\r'` 生成副本再上传，不动源文件。已用 CRLF 副本端到端验证。
- 教训：发布附件**不要直接传工作区文件**，尤其在开了 autocrlf 的 Windows 仓库；先确认换行符。
