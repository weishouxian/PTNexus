## 核实：DockerHub `fenglaile/ptnexus:latest` 只有 amd64，没有 arm64

实测（老卫在 Debian 上跑 `docker buildx imagetools inspect fenglaile/ptnexus:latest`）：manifest list 里只有 `linux/amd64` + 一个 `unknown/unknown` 的 **attestation-manifest**（buildx 的 provenance 证明，**不是** arm64，别误读成双架构）。

根因：`release-manual.yml` 的 `docker_image` job 虽写了 `platforms: linux/amd64,linux/arm64`，但 **CI 从未成功过** —— `gh run list --workflow=release-manual.yml` 显示每天 22:00 UTC 的 schedule 全部 failure，且每次都挂在 **meta job**（几秒即失败），`docker_image`/`proxy`/`runtime`/`desktop_windows`/`release_assets` 全部 skipped。所以 DockerHub 上的 latest 是**本地手工 buildx push** 的产物（Windows x64 → 单平台 + provenance），天然只有 amd64。

结论：CI 里的双平台配置是「意图」，线上镜像并未实现。要真出 arm64，要么让 meta job 不再失败从而跑通 CI，要么本地/服务器上显式 `--platform linux/amd64,linux/arm64` 构建推送。
验证命令（需能连 registry）：`docker buildx imagetools inspect <tag> --raw | jq -r '.manifests[] | "\(.platform.architecture // "attestation") \(.digest)"'`。

补充：`ghcr.io/weishouxian/pt-nexus` 匿名拉取返回 **403 Forbidden**（拿不到匿名 token）→ GHCR 包为**私有**或**从未推送**（GHCR 对两者都回 403）。本机 gh token 只有 `gist/read:org/repo`，缺 `read:packages`，`gh api /users/weishouxian/packages` 同样 403，无法进一步核实。按 CI 全失败的事实推断：GHCR 上不存在 CI 产物；对外实际可用的是 Docker Hub 的 `fenglaile/ptnexus`（公开、单 amd64）。要看 GHCR 需先 `gh auth refresh -h github.com -s read:packages` 或 `docker login ghcr.io`。

## BDInfo 溯源：arm64 版可自建（源码已定位）

老卫要求「arm64 镜像里 BDInfo 也能用」，因此把这三个预编译文件的来源挖清楚了：

- **来源 = `github.com/dotnetcorecorner/BDInfo`**（.NET 移植版，含 dotnetcorecorner 独有的 `BDInfoDataSubstractor` 子项目；祖上游是 `UniqProject/BDInfo`）。本地 `server/bdinfo/linux/` 三个文件与 `sqing33/PTNexus` 上游仓库**字节大小完全一致**（73097275 / 71185080 / 76640）→ 上游自己也没做 arm64。
- **技术栈 = .NET 9 self-contained 单文件**（`grep -a` 命中 `.NETCoreApp,Version=v9.0` / `Microsoft.NETCore.App` / `System.Private.CoreLib.dll` / `clr.dll`）。**不是 NativeAOT**（有 IL 化 CoreCLR 特征）→ 意味着 `dotnet publish -r linux-arm64` **在任何平台都能交叉产出**，不需要 QEMU/arm64 机器。
- **上游构建命令**（`.github/workflows/dotnet.yml`，只出 linux-x64 / win-x64）：
  `dotnet publish BDInfo.Core/BDInfo/BDInfo.csproj -c Release -r linux-x64 -p:PublishSingleFile=true -p:DebugType=None -p:DebugSymbols=false --self-contained`
  （`BDInfoDataSubstractor` 同法；`BDInfo.csproj` 里 `<RuntimeIdentifiers>win-x64;linux-x64</RuntimeIdentifiers>` 需补 `linux-arm64`。依赖只有 CommandLineParser 等纯托管包，无架构限制。）
- **liblzfse.so**：`BDInfoDataSubstractor` **完全不引用**（grep 0 命中）；`BDInfo` 二进制里有 11 处 lzfse 字样（`Lzfse`/`LzfseCompressed`/`LzfseCompressor`/`LzfseResource`/`LzfseAttribute`），但**两份源码里用 code search 都搜不到 lzfse** → 归属存疑。稳妥做法：arm64 目录里照样放一个 arm64 版 `liblzfse.so`（lzfse 是开源 C 项目，76KB，交叉编译简单），别省。
- 上游 `UniqProject/BDInfo` v0.8.0.1b **有现成 `BDInfo_v0.8.0.1b-linux-arm64.zip`**，但版本线与 dotnetcorecorner 2.x 不同、且没有 DataSubstractor → 不作为主路径。
- 落地还需：`server/bdinfo/linux-arm64/` 新目录 + `Dockerfile` 按 `TARGETARCH` 选择目录（当前是写死 `COPY ./server/bdinfo/linux/`）。

## ✅ BDInfo arm64 版已构建并入库（Docker 镜像多架构支持落地）

**版本确认**：老卫现用的 BDInfo 经实证为 **dotnetcorecorner 2.0.6 + lzfse-net 1.0.15**。依据两点：① 老二进制内含 `2.0.6.0` 版本串；② 老 `liblzfse.so` = 76640 字节，与 NuGet 包 `lzfse-net/1.0.15/runtimes/linux-x64/native/liblzfse.so` **字节完全一致**。

**关键技术点**：
- `liblzfse.so` **无需自己编**——它是 `DiscUtils`（BDCommon 依赖，处理 DMG/HFS+）的传递依赖 `lzfse-net` NuGet 包自带的原生库，包内含 `runtimes/{linux-x64,linux-arm64,linux-musl-x64}/native/liblzfse.so`，`publish -r linux-arm64` 会**自动选对架构**。源码里 grep `lzfse` 为 0 命中（只存在于 obj/bin 的依赖清单），别被这点误导。
- 构建命令（交叉发布，Windows 上就能出 Linux ARM64，不需 QEMU/ARM 机器）：
  `dotnet publish BDInfo.Core/<Proj>/<Proj>.csproj -c Release -r linux-arm64 -p:PublishSingleFile=true -p:DebugType=None -p:DebugSymbols=false --self-contained`
  前置：`BDInfo.csproj` 与 `BDCommon.csproj` 的 `<RuntimeIdentifiers>` 要补 `linux-arm64`（否则报 RID 不支持）。`BDInfoDataSubstractor.csproj` 无 RID 列表、无需改。
- 工具链（**隔离安装，未污染系统**）：从 `builds.dotnet.microsoft.com` 拉 SDK **9.0.318** zip（298MB）解压到 `C:\Users\wind\.workbuddy\binaries\dotnet-sdk\9.0.318`；用时设 `DOTNET_ROOT` + 独立 `NUGET_PACKAGES`。首次 restore 约 20s，单个项目 publish 约 25s。
- 产物校验：三件均为 **ELF64 / AArch64 / ET_DYN**，interpreter `/lib/ld-linux-aarch64.so.1`，DT_NEEDED 正常。大小：`BDInfo` 80215202、`BDInfoDataSubstractor` 78190457、`liblzfse.so` 77488（比 x64 版大 ~7MB，源于 runtime 补丁版本 9.0.3xx vs 9.0.1xx，功能无差异）。

**入库改动**：
- `server/bdinfo/linux/` → 重命名 `server/bdinfo/linux-amd64/`；新增 `server/bdinfo/linux-arm64/`（三件套）。
- `Dockerfile`：加 `ARG TARGETARCH`（BuildKit 自动注入 amd64/arm64），`COPY ./server/bdinfo/linux-${TARGETARCH}/ /app/bdinfo/linux/`。**容器内路径 `/app/bdinfo/linux` 保持不变**——Go 侧只认 `PTNEXUS_BDINFO_DIR`/`_PATH` 环境变量，不关心源目录名。仓库内除 Dockerfile 外无其他 `bdinfo/linux` 硬引用。
- 注意：`.workbuddy/tmp` **未进 .gitignore**，构建中间产物（191MB）已手动清理，避免误提交。

**待验证（本机 WSL 被安全策略禁用，无法自测）**：需在 Debian 上用 `docker run --privileged --rm tonistiigi/binfmt --install arm64` 注册后，以 `--platform linux/arm64` 实跑 `BDInfo --help`。

**⚠️ 遗留性能坑**：`buildx` 多平台构建时，Dockerfile 的 `server-builder` stage 是 `CGO_ENABLED=1`（mattn/go-sqlite3），会在 **QEMU 模拟 arm64 下编译**，可能耗时十几到几十分钟。提速方案：该 stage 改 `FROM --platform=$BUILDPLATFORM` + 装 `gcc-aarch64-linux-gnu libc6-dev-arm64-cross` 做真交叉编译（CI 的 runtime job 已有此写法可参考）。本次未改，属独立优化项。
