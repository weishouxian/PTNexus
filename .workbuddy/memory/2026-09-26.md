## 结论：下载器「发布节奏」两项设置的真实语义（代码核对）
- **唯一消费点**：`server/internal/service/autoseed/service.go` `resolveDownloaderPublishSettings()`（读 config JSON 里 `downloaders[].publish_interval_minutes / publish_concurrency`，按条目 `downloader_id` 匹配），只被 `PublishItems()` 调用（自动发种页手动发布 + 规则命中自动投递，两者共用）。无其它读取处。
- **算法**：`wave = idx / concurrency`（idx 为目标站序号），`wave>0 && interval>0` 才写 `scheduled_at = now + wave*interval`；第 1 波立即入队。例：3 站 / 并发 2 / 间隔 5min → A、B 立即，C 5 分钟后。
- **实际效果是错峰而非真并发**：队列消费 `migrationflow.publish_queue.go` `drainPublishQueueOnce()` 每次 tick 领 `MaxWorkers`(默认 1，上限 20) 条但**同步逐条执行**，`MonitorIntervalSec` 默认 30s，到点条件 `scheduled_at IS NULL OR scheduled_at <= now`。所以「并发数」= 同一时间点入队的站数，真实同时发种数仍受队列处理速度限制。
- **不生效的地方**：①「一种多站」批量发布用 `migrationflow/publish_batch.go` 的 `publish_batch_concurrency_manual`（默认 5，上限 200，按 CPU 核数给建议，见 `settings/cross_seed_settings.go`）；②「定时发种」`scheduledseed` 用任务自身的 `IntervalMinutes`，完全不读下载器节奏。
- **死字段提醒**：`auto_seed_rules` 表也有 `publish_interval_minutes / publish_concurrency` 列，但 `AutoSeedView.vue` 的 `saveRule()` **硬编码**提交 `0 / 1`，且后端除归一化校验外无任何消费点 —— 规则级那两个字段是历史遗留，别误以为生效。

## 修复：「下载器发布进度」时间显示成 UTC（已提交 8da54b8）
- 老卫现象：进度页「实际发布时间」显示 `2026-09-26T17:33:02Z`（带 Z 的 UTC），而「加入队列」显示 `2026-09-26T16:35:21Z` —— 看着像本地时间其实是 UTC。
- **根因**：`repository/db.go:53` MySQL DSN 用 `loc=Local`。容器 `TZ=Asia/Shanghai` 让 Go 的 `time.Now()` 出北京时间，但容器 **`/etc/localtime` 是 `Etc/UTC`**（compose 只设了 TZ 环境变量，没 `ln -sf /usr/share/zoneinfo/Asia/Shanghai /etc/localtime`）→ **`time.Local` 解析成 UTC**。链路：Go 写北京墙钟文本 → MySQL 文本列存的是北京值 → 驱动按 UTC 解析读回 → 前端原样渲染，**早 8 小时**。
- 证据链（OVH 实测）：`date` → `CST`；`readlink -f /etc/localtime` → `Etc/UTC`；MySQL `@@time_zone=SYSTEM`、`NOW()=UTC_TIMESTAMP()`；MySQL 容器 `1Panel-mysql-Rzk5` 当时是 **Exited (137) 6 天**（应用自 9-21 起 FATAL 连不上 DB，5274 返回 502），手动 `docker start` 后恢复。**注意 `1Panel-mysql-Rzk5` 走 23330 端口，`ss` 在宿主机看不到（Docker 的 DNAT 规则不经内核 LISTEN 表），别据此判断 MySQL 没跑；`docker ps -a` 里查才是准的。**
- 修复（`server/internal/repository/db.go`，+32/-2）：
  - 新增包级 `DatabaseTimeZone = resolveDatabaseTimeZone()` —— 优先 `time.LoadLocation("Asia/Shanghai")`，失败退回 `time.FixedZone("CST", 8*3600)`（容器可能缺 tzdata）。
  - MySQL DSN：`loc=Local` → `loc=` + `url.QueryEscape("Asia/Shanghai")`（DSN 值需 URL 转义）。**不能用 loc=Local，容器里它就等于 UTC。**
  - PostgreSQL DSN：`TimeZone=Asia/Shanghai` 硬编码 → `DatabaseTimeZone.String()`，两种驱动同一来源。
- ⚠️ 存量数据已混在一起，**修完只保证新写入读回正确**，历史 `started_at/finished_at` 的零点取决于写入时进程环境（本地跑=北京、线上跑=北京、只有 MySQL 容器自身 `NOW()` 才是 UTC）。要修历史只能按来源逐条判断，别一刀切减 8 小时。
- 验证：`go build ./...`、`go vet ./internal/repository/`、gofmt（`tr -d '\r'` 后）全过。**未部署**（老卫选了「只提交，我自己推」）。
