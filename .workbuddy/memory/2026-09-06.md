# 2026-09-06

## 排查：发种后源站地址被改（已定位，未修复）

现象：发种（publish）成功后，源站种子在种子列表里的详情页地址变成目标站的链接。

根因链路：
1. `service/publish/workflow/publish_entry.go:321` `publishedHashCandidates := collectPublishedTorrentHashes(input.SourceTorrentHash)`
   —— 回写用的 hash 是**源种子 hash**（`publish_with_context.go:71` `SourceTorrentHash: input.Context.Hash`）。
2. `publish_entry.go:357` 组装 `PublishTorrentDetailsUpdateInput{Hashes: 源种hash, SiteNickname: 目标站昵称, DetailsURL: publishURL}`。
3. `repository/migrate_repository.go:500 UpdateTorrentDetailsAfterPublish`：
   - 第 530 行先按 `hash + sites=目标站昵称` 更新 → 通常 0 行（torrents 表该 hash 的行 sites 是源站）；
   - 第 535 行**兜底去掉 sites 条件**，只按 hash 更新 → 命中源站行，把源站 details 覆盖成目标站详情页 URL。❌
   - 第 544 行 name+site 兜底带 sites 条件，安全。

修复方向：删除 `updateBy(false, ...)` 这一级兜底；且 `siteNickname == ""` 时应直接返回 0，不做无站点限定的回写。等用户确认后再改。

## 其他结论：sites 表写入点（用于后续排查站点配置被改）

只有 6 处：
- `repository/sites_sync.go:141/187` 启动时 `SyncSitesFromJSON`，**无条件覆盖 base_url/nickname/site/special_tracker_domain**，只保护 cookie/passkey/speed_limit/ratio_threshold/seed_speed_limit（`bootstrap/app.go:49`）。
- `repository/site_repository.go:148` 站点管理保存（`/api/sites/update`）；`:197/:209` cookie；`:279` sort_order。
- 发种链路（publish/publisher/migrationflow）**不写 sites 表**。

坑：`repository/migrate_repository.go:230 GetSiteByName` 用 `nickname = ? OR site = ?` + `Limit(1)` 且**无 ORDER BY**，多站同名/交叉匹配时命中行不确定；`migrationflow/publish_logs.go:569 normalizePublishLogSourceSite` 依赖它把源站名改写成 nickname，可能"源站被显示成另一个站"。
- `sites_sync.go:261 registerSiteIndex` 把 site/nickname/base_url 混在同一 map 做 key，存在串行覆盖风险。
