## 22:10 排查：下载器里「名字是 40 位 hash、大小 0 B、状态=下载元数据」的空壳任务

**用户问题**：截图里两条红框任务（名称 `c7d09a60...798de`、`582645e1...fea50`）为什么会在下载器里。

**结论**：这不是"没下完的种子"，而是**只有 infohash、从没拿到元数据的空壳任务**（名称=hash、选定大小 0 B、状态「下载元数据」、已完成 0.0%）。qB 只在「添加时只拿到 infohash」时才会建这种条目。

**对照实验（在 ovh_15 下载器 5.135.178.15:8181，qB 4.6.7 上做，测完即清理）**：
- 把非种子内容（HTML）当 URL 交给 `torrents/add` → qB **什么都不建**（任务数 5910 不变）。⇒ 发布流程走 HTTP 直链那条路**不会**留下这种空壳。
- 只给 infohash 的磁力（`magnet:?xt=urn:btih:...&dn=xx`）→ 立刻建出同形态任务（size 0 / total_size -1 / state metaDL）；**磁力里没有 `dn` 时名称就直接显示 40 位 hash**。
- 清理命令：`/api/v2/torrents/delete`（hashes + deleteFiles=false），事后任务数回到 5910。

**代码侧取证**：
- `server/internal/service/publish/downloader/add.go` 三条加种分支：本地 .torrent（108/117）、详情页抓 .torrent 后按数据加（136）、兜底把 URL 原样交给下载器（153 `AddTorrentURLWithOptions`）。日志文案分别是「已通过本地种子文件添加到下载器」/「已从详情页下载种子并添加到下载器」/「已通过 URL 添加到下载器」——排查时可直接搜这三句。
- 标签 `站点/<站点名>` 只由 `add.go:304-327 resolveConfiguredTagsAndCategory` 生成（`站点/{站点名称}` 占位符，且 `tags.enabled=false` 时该占位符**依然生效**）；分类关闭 → qB「分类」列全空，与截图一致。
- 全仓 grep `magnet`（排除 node_modules/.git/.worktree-lite/dist）**零命中**（只命中 BDInfo 二进制）⇒ PTNexus 自己从不构造磁力。所以空壳的 infohash 只能来自外部输入（手动加种贴磁力 / 别的工具先以磁力加过、PTNexus 随后把 `站点/x` 标签补写到同 hash 的已存在任务上 —— `applyTorrentTagsWithRetry` 是独立第二步，qB 按 infohash 去重不新建任务，这条能同时解释"hash 当名字 + PTNexus 站点标签"）。

**顺带发现（基础设施）**：OVH 5.135.178.15 上 `pt-nexus` 与 `1Panel-mysql-Rzk5`（Exit 137）等容器**9 小时前已退出**（MySQL 是被 OOM kill 的），即该机 PTNexus 当前是停的；同机 `1Panel-qbittorrent-t9KM`（qB 4.6.7，5908~5910 个任务，admin/111111）仍在线。config.json 里配了两台下载器：`ovh_15`(5.135.178.15:8181) 与 `86`(37.120.173.86:8181)；但 `86` 从 OVH 与本机都连不上（超时），走 9090 盒子代理也是 404。**截图里那两条空壳不在这两台可查的 qB 之外的那台 = `86`/本地那台**（ovh_15 按 hash 查返回空）。

## 22:45 追问梳理：「已经在一种多站删掉了，为什么又被自动发种推回来」

**用户问题**：那条种子已在「一种多站」(/torrents) 删过，为什么还会触发自动发种/发种程序。

**关键认知：这是两条独立通道，别混在一起看**

1. **发布流程的自动加种（最可能的"删了又回来"）**
   - 队列里每条发布任务的 payload 都写死 `"auto_add_to_downloader": true`（`server/internal/service/migrationflow/publish_queue.go:520`），workflow 侧在发布成功后调 `AddToDownloader`（`publish/workflow/publish_entry.go:312-357`，`url = directDownloadURL 优先，否则 publishURL`），成功后按 `站点/{站点名称}` 补标签。
   - ⇒ 只要这条种子还在**定时发种任务**（`scheduled_seed_tasks.seeds`）的列表里，或还在自动发种的转种目标里，**每次发布都会把它重新加回下载器** —— 这条通道完全不看下载器当前有没有、也不看 auto_seed_items 是否 retained。
2. **定时发种的查重只认 publish_logs**
   - `ScheduledSeedRepository.CheckDuplicate` 只查 `publish_logs`（torrent_id+source_site+target_site+scene='scheduled_seeding'+status='success'）。
   - 「一种多站」删种**不碰** publish_logs，也**不碰** scheduled_seed_tasks 的 seeds（`torrentdata/delete.go` 只做三件事：删下载器任务/文件、删 `torrents` 行、把命中 hash 的 auto_seed_items 标 retained）。
3. **RSS 自动发种侧：retained 本身不会自动重推**
   - `shouldRetryAutoSeedItem`（`autoseed/service.go:1459-1474`）对 `retained` 明确 return false。
   - 会重推的只有四种：① 记录不存在（在自动发种页删记录 = 物理删除，`service.go:919-935` `repo.DeleteItems` → RSS 窗口内必然重新下发）；② guid 变了（站点重发/改种、或 RSS guid 不稳定）→ `UpsertItem` 按 `rule_id+guid` 查不到当新条目；③ 状态停在 `pending` 或被标为**可重试失败**（`isRetryableAutoSeedRejectReason`：详情页数据抓取失败 / 推送下载器失败 / 未获取到源站标签 / 未获取到源站详情 / 未获取到下载器）；④ 手动「重新推送」`PushItems`（retained 的唯一恢复入口，`MarkItemPushed` 清 retained_at）。
4. **retained 漏标的三个条件**（`MarkItemsRetainedByHashes`，`repository/auto_seed_repository.go:543-580`）
   - 只匹配 `LOWER(downloader_hash) IN (...)`（hash 为空就漏）；只覆盖 `pushed/organized/published`；只有 `delete_files=true` 时才会被调用（`torrentdata/delete.go:96`）。

**关于那两条 hash 空壳的补充线索**：截图放大后两条分别带 `站点/三月传媒`(17:26:20) 与 `站点/自由农场`(17:26:53) 标签；种子列 `0(1)`/`0(2)` 说明**能找到 peer** ⇒ 加种时给的是**带 `tr=` 的磁力链接**（没有 `dn` 才显示成 hash）。所以"被重新加回来"和"加的是磁力而非 .torrent"是两个现象：前者是发布流程的 auto_add，后者说明那次 directDownloadURL/publishURL 实际是磁力（需看发布日志里「直链下载:」那一行确认，publish_entry.go:206 会写进去）。

**可加的护栏（待用户确认再改）**：① `add.go` 拦截 `magnet:`/裸 hash（或改为服务端用站点 cookie 抓 .torrent 再以数据加种）；② 加种后异步校验 `metaDL && 0 字节` → 删除任务并记日志；③ 定期清理下载器里的 metaDL 空壳。

## 23:2x 落地护栏①：「一种多站」删种时作废对应 publish_logs 的已发布记录

**背景**：上一条护栏 ③ 被用户选中执行 —— 删种后不要再被定时发种重新发一遍。
