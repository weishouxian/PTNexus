## 代码梳理：一种多站（/torrents）删除按钮逻辑（只读分析，无改动）

**调用链**：`TorrentsView.vue:406-413` 按钮 → `deleteTorrentRow`（1725-1777）→ `POST /api/data/delete`（`bootstrap/app.go:304`）→ `torrents_data_handler.go:84` → `torrentdata/delete.go:18 DeleteTorrentByHash` → `repository`（`ListTorrentsByHashes` :408 / `DeleteTorrentsByHashes` :433）→ `downloaderclient/client.go:104 DeleteTorrents`（qB `torrents/delete` + `deleteFiles`；TR `torrent-remove` + `delete-local-data`）。

**梳理出的三个非显然行为（重要）**：

1. **删除范围是「该种子在所有下载器上的全部副本」，与页面下载器筛选无关。**
   - 聚合 key = `name\x00size`（`data.go:66`），`Hashes` 收集该 key 下所有 `row.Hash`（`data.go:88-93`）。
   - `ListTorrents`（`data.go:41`）**不带任何筛选**，`applyFilters` 在聚合**之后**才执行（`data.go:205`，`filtering.go:49` 按 `item["downloaderIds"]` 求交集）。
   - → 筛选下载器 A 后点删除，`hashes` 仍含 B/C 的副本，`delete_files=true` 时 A/B/C 上的任务全删。
2. **「只删除记录」是临时的。** 只删 DB、不动下载器；下次刷新时 `SyncDownloaderTorrents` upsert 会带 `IsHidden: 0`（`torrent_sync_repository.go:247`）把记录**写回**。要彻底消失必须删下载器任务。
3. **跨下载器无事务。** `delete.go:49-62` 逐组删下载器，任一失败立即 return 502 且**不删 DB**；此前已成功的下载器任务无法回滚 → 出现「任务已删、DB 仍有记录」，需等下次刷新按 `missing_in_snapshot` 隐藏。

**其他**：`delete_files=true` 且某行 `row.Downloader` 为空 → 400 整体拒绝（但分组在删除前完成，不会删一半才报错；这类行只能用「只删记录」）；`ListTorrentsByHashes` 带 `is_hidden=0` 过滤，已隐藏记录查不到（404）；确认框 `cancelButtonText='只删除记录'` 没有真正的「取消」按钮，只能按 Esc/X（靠 `distinguishCancelAndClose: true` 区分）；`batch-action-bar` 只有批量发种，**无批量删除**；`deleteTorrentRow` 首行 `=> {\tconst hash` 缺换行且函数体 tab/空格混用，prettier 可修。

## 代码梳理：自动发种「种子被删后会不会重新下载」（只读分析，无改动）

**结论：不会重下。** 自动发种的去重只认 `auto_seed_items` 的 `rule_id + guid`，不检查下载器里是否还有这个种子。

- 去重键：`UpsertItem` 按 `rule_id + guid` 幂等（`auto_seed_repository.go:287-304`）；guid 取 RSS 的 `entry.GUID`，缺省退化为 `stableID(torrentURL + title)`（`autoseed/service.go:1076`）。
- 命中后分流：`shouldRetryAutoSeedItem`（`service.go:1456`）只对 `pending` 或「可重试的 rejected」返回 true；`pushed` / `organized` / `published` 一律跳过（`service.go:245-258` 直接 continue）→ 不抓详情、不推下载器。
- 手动「推送」按钮同样拒绝这三类状态（`PushItems`，`service.go:663-667` 返回「已推送或已进入后续流程」）。

**会重下的 4 条路径**：① 记录被删（自动发种页面删除 / **保种到期清理 `deleteRetainedSeed` → `DeleteItems`**）；② RSS guid 变化（站点重发种）；③ 状态为 pending 或可重试 rejected（`ResetItemForRetry`）；④ 规则过滤条件变化后重试。

**⚠️ 已识别的设计缺口（待用户决定是否修）**：保种清理在删下载器任务+文件之后**连 `auto_seed_items` 记录一起删**（`service.go:997 / 1047`），等于删掉了去重凭据。只要站点 RSS 窗口内还能拉到同一条目，下一轮就会重新抓详情 + 重新下载 → 「删了又下、下了又删」循环。可选修法：保种清理改为**保留记录并打标记**（推荐）、或加「已删除」状态 + 页面「重新推送」按钮。

**`deleted_from_downloader` 只是展示标记**：结构体 `gorm:"-"`，在 `enrichItemSavePaths`（`service.go:1608-1645` / 无 repo 分支 1669-1674）计算——`torrents` 表查不到 hash 且下载器实时任务列表也匹配不到才置 true。不落库、不参与决策；且 `downloader_hash` 为空时直接跳过判定（1605），这类记录永远显示正常。

**顺带**：`DownloadTorrentForSource`（`acquire/fetch/torrent_fetch.go:206-217`）**无本地缓存判断**，每次实打实下载并写入 `data/tmp/torrents`（文件名带纳秒），所以「拉取种子」只要走到这一步就一定重新下载。

## 排查「点刷新按钮没反应」：互斥拦下 + 前端假成功

**现象**：用户点顶部刷新，界面提示已刷新但数据没变（日志 `POST /api/refresh_data` 全部 0s 返回）。

**排查链路（日志是关键证据）**：
1. `curl -X POST /api/refresh_data` 手动验证 → 返回 `{"success":false,"message":"种子数据更新正在进行中，请稍后再试"}` → 确认是 `refreshRunning` 互斥标志被占。
2. `server/data/logs/ptnexus.log` 里翻到决定性一行：`21:55:28 | 200 | 6m14s | ::1 | POST "/api/refresh_data"` —— **一条耗时 6 分 14 秒的全量刷新**，起始于 21:49:14。
3. 该请求**不是**定时任务（`/api/settings` 显示 `torrent_refresh_enabled=false`，且 interval=30min 首次 tick 在 22:14）→ 追到源头是**前端 `publishFlow.ts` 在发种完成后自动调 `/api/refresh_data`（不带 downloader_id = 全量）**，两处（:362 / :691）。
4. 全量刷新要同步 `15` 号下载器 **5559 个种子**（21:55:27 日志 `updated=5548 fetched=5559`）+ NC 102 个 → 正好 6 分多钟。
5. 用户在这 6 分钟内点刷新全被拒，而 **`App.vue` 的 `handleGlobalRefresh` 与 `TorrentsView.syncDownloadersAndReload` 都不判断 `response.data.success`** → 照样弹「数据已刷新！」→ 用户看到的就是"点了没反应"。

**结论：刷新逻辑本身没坏（21:45:13 / 21:47:20 的手动刷新都成功了），坏的是「被拒时前端假装成功」+「发布后全量刷新长时间占锁」。**

**改动**：
- 后端 `service/torrentdata/`：
  - `types.go`：`TorrentDataService` 新增运行态快照 `refreshTrigger` / `refreshStartedAt` / `refreshTargets`。
  - `refresh_sync.go`：`beginRefresh(trigger)` 记录来源与起始时间；新增 `setRefreshTargets` / `refreshBusyResult` / `downloaderNames` / `formatRefreshElapsed`；busy 时返回 `{success:false, busy:true, message, running:{trigger,downloaders,elapsed_ms}}`，提示形如「后台定时刷新正在进行（目标：15、NC，已运行 6 分 30 秒），请稍后再试。」；新增「开始刷新 trigger=… downloaders=…」日志（之前任务开始阶段完全无日志，是排查困难的主因）。
  - `iyuu.go`：`RefreshData` 固定标记为手动来源；新增 `refreshScheduled()`（定时专用）。
  - `auto_refresh.go`：改调 `refreshScheduled()`。
