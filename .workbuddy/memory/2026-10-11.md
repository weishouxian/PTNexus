## 澄清：音频编码「组件值」与「标准键」是两套口径

- 现象追问：修完 `audio_codec`（→ `audio.ddp`）后，面板组件仍显示 `DDP 5.1 11Audios`。
- 根因：**组件「音频编码」对 MediaInfo 源走「标题优先 + 媒体补缺」**，不是「媒体首轨」。
  - `title/components.go:56` 把 `isBDInfo` 当 `preferMediaAudio` 传给 `media.ApplyMediaInfoOverrides`；只有 BDInfo 源走媒体首轨重建（`overrides.go:37`），MediaInfo 源走 `:45-67` 标题优先。
  - 所以 `DDP`/`5.1` 来自标题，`11Audios` 来自媒体（`parser_pythonish.go:358`，MediaInfo 且音轨数>1）。
- ⚠️ 媒体侧「第一条音轨」= **物理 tracks[0]**（`buildMediaInfoAudioFromTracks` 的 `best := tracks[0]`），不是主音轨。本样本 Audio #1 是 `AAC LC 2.0 捷克语 Default:Yes`（配音轨）⇒ 若只把 MediaInfo 源切成媒体优先、不动选轨，组件会变 `AAC 2.0 11Audios`。
- 要得到「主音轨的 编码+声道+Atmos+音轨数」须两步：① MediaInfo 源也走 `preferMediaAudio=true`；② 媒体侧选轨复用 `acquire/extract/mediainfo_codec.go:audioCodecKeyForInference` 的「跳过低规格配音轨」规则。依赖方向 OK：`processing/media` 已 import `acquire/extract`（`parser_pythonish.go:8`），`exports.go:56` 已导出 `SelectAudioTrack(tracks, policy)`。
- 待用户拍板 A（严格物理首轨 → `AAC 2.0 11Audios`）/ B（主音轨 → `DDP 5.1 11Audios`，来源统一）后再改。

## 按方案 B 落地：组件「音频编码」统一取媒体主音轨

用户拍板 **B**（组件值 = 主音轨的 编码+声道+Atmos+音轨数，且全部出自媒体）。改了 4 个文件：

1. `acquire/extract/mediainfo_codec.go` 新增两个**导出件**供媒体侧复用同一套规则（不自写第二份规格表）：
   - `SelectInferenceAudioTrack(tracks []AudioTrack) AudioTrack` —— 包装 `audioCodecKeyForInference`，返回被选中的那条音轨而非只返回 key。
   - `AudioCodecKeyFromDisplayName(display string) string` —— 展示口径编码名（`standardAudioCode` 的产出：DDP/TrueHD/`DTS-HD MA`/`DD`/LPCM…）→ 标准键字典。⚠️ 裸 `DD` 是 Dolby Digital 有损 → 映到 `audio.ac3`（不是 `audio.ddp`）。
2. `processing/media/parser_pythonish.go`：`buildMediaInfoAudioFromTracks` 的 `best := tracks[0]` → `best := pickMainAudioTrack(tracks)`；新函数把 `parsedAudioTrack` 映射成 `[]extract.AudioTrack{CodecKey}` 后调 `SelectInferenceAudioTrack`，再按 CodecKey 首命中回映原索引。
3. `processing/title/components.go`：`ApplyMediaInfoOverrides(..., isBDInfo)` → `..., true`（MediaInfo 源不再走标题优先）。副作用：「标题优先 + 媒体补缺」分支（`findBestMatchingAudioTrack`/`supplementAudioInfo`）暂无调用方，保留备用。
4. `processing/media/overrides.go` 仅改注释与分支说明。

### 顺带修掉的真 bug：`Channel(s)` 正则永远匹配不上

- `parser_pythonish.go:250` 从 Python 直译时把 raw string 写成了 `Channel\\(s\\)` —— Go 反引号 raw string 不处理转义，正则要求**字面反斜杠**，`Channel(s) : 6 channels` 从未被解析。
- 后果：**只有 `Channel(s)` 没有 `Channel layout` 的 MediaInfo，声道一律退化成 `2.0`**（本样本恰好有 `Channel layout`，所以之前没暴露；E2E 用例用的是只有 `Channel(s)` 的简化样本，直接把 `DDP 5.1` 打成了 `DDP 2.0` 才暴露）。
- 已修为 `Channel\(s\)`。⚠️ 同文件 `:417 cleanBBCode` 的 `\\[/?\\w+\\]`（应为 `\[/?\w+\]`）是**同类问题，未修**（BDInfo 链路、blast radius 更大，待用户确认）。
- 影响面：BDInfo 路径不用这个正则（用 `(\d+\.\d+)` 从整行取），故无 BDInfo 回归。

## 打包单文件桌面 exe（前端 + 内嵌 server）

- 需求：把项目打成「一个包含前后端的 exe」。走现成脚本 `bash scripts/package-desktop.sh single`（见 `desktop/docs/build.md` 第一节），无需 wails CLI / NSIS / rsync / gcc。
- 命令（Windows Git Bash 必须先补 PATH）：
  `export PATH="/d/go/go1.25.11/bin:$HOME/AppData/Roaming/npm:/c/Program Files/Git/cmd:$PATH" && bash scripts/package-desktop.sh single`
- 三阶段：① `prepare_frontend_stage`（`pnpm -C webui run build` → 同步 `webui/dist` 到 `desktop/frontend/dist`，供 go:embed）② `sync_embedded_bundle`（`server/sites_data.json` + `server/configs/` → `desktop/internal/desktopapp/bundle/`）③ `go build -tags desktop,production -ldflags "-w -s"`。
- 产物：`desktop/build/bin/pt-nexus.exe`，38.17 MB，构建耗时 ~17s。首启动自建 `%APPDATA%/pt-nexus` 并把内嵌站点资源展开到 `resources/`，无需外挂文件。
- 校验手段（无需启动 GUI）：`grep -qa <资源名> exe` 验内嵌前端 hash 资源（如 `index-*.js`）与站点资源名；PE 头 `MZ`。
- 副作用：`sync_embedded_bundle` 会改写 git 跟踪的 `desktop/internal/desktopapp/bundle/sites_data.json`，并可能新增 bundle/configs 下站点 yaml（本次新增 `52pt.yaml`）——提交时注意一并带上。
- 若要 NSIS 安装包（含 server.exe/updater.exe sidecar）则跑不带参数的 `package`，需 makensis —— 本机未装。
